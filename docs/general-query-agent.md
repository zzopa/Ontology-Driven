# 通用问数智能体：准确查询与证据分析分层

更新：2026-10-08。目标是保留已有可核验的查询输出，在其上提供有依据的分析与内容编排，不按企业名称、人员姓名或单个问题写专用回答。

## 统一工作流与边界

问题先进入本体检索和计划解析。计划区分筛选锚点、明细目标、统计对象、条件所属表、业务时间和指标；编译器生成参数化只读 SQL，执行后保留原始明细与来源事实。证据分析模型读取完整分批证据，输出有事实引用的发现、解释、限制或建议。最后的编排模型只组织这些结论，不能再次改写数字或新增正文。

本轮不改数据库业务记录，不增加外部图数据库，不创建独立模型服务或新账号，不修改管理员当前选中的模型。模型不拥有数据库连接，也不能生成直接执行的任意 SQL。建议、解释不是数据库事实；来源/数字/单位检查不是完整语义证明。

## 全模块统筹

| 模块 | 职责与本轮状态 | 后续缺口 |
| --- | --- | --- |
| 元数据、本体 | 沿用启动刷新、字段注释、单位、枚举、身份/时间绑定、关系路径和版本；不新增某企业专用规则 | 企业实体消歧、业务关系审核、复合指标口径仍需完善 |

| SQL、权限 | 继续使用原编译器、参数绑定、去重、分页、EXPLAIN、只读连接及行列授权；不向模型开放绕过入口 | 差额/比率/排名等复合指标需要新增安全计算能力，不能靠模型心算 |
| 事实、传递 | 明细、字段解释、来源键、实际关联、单位、时间、完整性保留；原有无损分批和逐段权限检查继续生效 | 已读取数据不等于数据库全部匹配行；读取上限保持不变 |
| 证据分析 | `app/agent/prompts.py` 统一策略：发现、解释、证据限制、核对建议；明细和数据库 COUNT/SUM 结果均可进入分析 | 不根据单批或片段推断全量；未实现自由的跨批新结论综合或自动推导新数字 |
| 内容编排 | `app/agent/response.py` 读取全部已核验结论，返回引用分组和顺序；每条恰好保留一次；不能新增正文、改分类或丢引用 | 不是让第二个模型自由重写事实；新分析必须先走证据核验 |
| 流式/UI | 确定性摘要先到，合格批次随到随发；最终按查询事实、主要发现、分析解释、证据边界、建议分组；旧会话无文档时兼容原正文 | 首段不等待编排，但额外编排请求仍可能增加总耗时 |
| 会话/审计 | 原加密快照保存 `query_summary`、`claims`、`answer_document` 和执行过程；权限变更后仍隐藏旧快照 | 本轮不修改历史错误答案，不给旧会话伪造分析文档 |
| 管理/配置 | 模型继续统一配置和请求上下文冻结；新增编排开关、预算、超时写入配置文件，并在后台只读运行参数中展示 | 未新增任意系统提示词编辑入口；业务口径仍通过版本化本体管理 |
| 验证 | 跨领域、所有物理表重命名、关联条件归属、失败回退、完整结论、前端旧快照和会话保存回归 | 固定样例通过不等于任意业务问题准确率 100% |

## 查询角色协调规则

“筛选锚点”不必等于“统计实体”。例如一个对象及其关联事项，锚点用于保留身份/企业条件，关联事项可作为 COUNT/SUM 粒度；引擎不针对具体表名分支。

允许协调的前提：关联对象在规则解析的 `focus_tables` 中，路径在当前授权本体中合法且不歧义。只连接在图上但问题未明确请求的对象不能随意替换。模型条件没写 `table` 时，先绑定到模型原主体，不能把同名字段重新绑定到锚点。之后仍合并并保留确定性的企业、姓名、时间条件，并通过原编译器白名单检查。没有映射、未知字段、多路径或真正的业务歧义仍拒绝或要求澄清。

这解决的是共性的查询角色冲突，不保证所有自然语言意图均已覆盖；简称身份、付款/履约含义、状态编码不能因技术关系成立就视为已知。

## 输出契约

- `query_summary`：原有确定性查询摘要。原来的 `answer`、`claims`、明细、SQL 和来源字段继续保留。
- `claims[].kind`：可选分类 `findings` / `interpretation` / `limitations` / `recommendations`；旧结论无分类时兼容为发现。模型不能自行声明 `query_facts`。
- `answer_document`：`version=evidence-answer-v1`、编排模式、原因、查询事实条数、全部结论条数，以及 `sections[{kind,title,claim_ids}]`。`C1` 等只引用本次 `claims` 的位置；标题来自固定词典，不由模型自由生成。所有结论恰好出现一次，查询事实放首组。
- 流式解释和建议也有明确文字标识；最终文档只改变阅读分组/顺序，不修改原结论。复制回答包含分组标题；旧客户端仍可读取原 `answer`。
- `timings.composition` 与实际执行步骤 `answer_layout` 单独记录编排耗时。报告明确 `semantic_proof=false`，不冒充已经证明无任何幻觉。

## 配置与失败策略

`config.json` / `config.local.json` 的 `query` 配置：

```json
{
  "answer_composition_enabled": true,
  "answer_composition_budget": 18000,
  "answer_composition_timeout_seconds": 20
}
```

预算是编排输入 JSON 字符数，不是原始查询取数上限。超过预算时不截断结论、不只送前几条，直接用完整确定性分组。编排最多一次请求，无额外重试；超时、网络失败、未知引用、遗漏、重复、改分类或新增正文都回退，保留准确摘要和全部合格结论。原始数据仍按原证据预算完整分批发送。没有合格附加分析、未启用模型或关闭编排时，不新增编排请求。

## 后续按共性能力推进

1. 统一实体解析：来自数据库、权限范围内的企业/相对方/人员候选，给出真实候选和结构化澄清，不自动生成某公司简称。
2. 声明式指标与安全计算：粒度、去重键、业务状态、单位、币种、日期和覆盖要求；补齐跨表差额、比率、排名和周期比较，并用数据库/确定性代码计算。
3. 受控多查询规划：一个问题拆成多个明确的子查询，统一权限、时间和实体范围，限制次数/预算；只使用现有白名单编译器，不开放任意 SQL。
4. 跨批综合分析：聚合各子查询的可核验证据与计算事实，保留关联上下文和来源；不把多个不完整批次的局部判断冒充全量结论。
5. 管理与评估：复合指标审核/版本、澄清会话状态、模型费用与延迟预算、跨业务与新增表的持续回归。

未完成上述能力前，不把本轮称为完整的自主多轮智能体。第一轮完成的是通用规划协调与事实—分析—编排分层。
