# 正文逐段输出优化（2026-10-05）

## 原因与改动

原流式接口已有 `progress` / `step`，但 `answer_delta` 直到所有证据批次完成才发出。某批模型响应较慢时，用户只能看到执行步骤，误以为停止处理；正文还嵌在 busy-only 进度卡中，停止或失败就消失。

- `app/core.py`：数据库证据生成后先发送确定性摘要；模型各批返回并通过来源、数值、单位核验后立即追加。原始证据仍完整分批传递，不通过减少记录提速，不输出未核验 token。最终正文与流式正文顺序一致，重复结论/警告去重。
- `app/planner.py`：条件完全覆盖的单一精确姓名查询走本体规则，跳过不必要的模型计划请求；多姓名、额外部门/性别、时间和关联业务不套用此快速路径。
- `do_ask`：在每次 `answer_delta` 前检查权限版本；回调异常不被吞成普通模型失败。
- `frontend/components/workspace.tsx`：实时正文单独展示，首段到达后显示“已查到结果，正在补充解读”；停止或断线保留已收到部分，标注“未完整完成”。执行过程和真实耗时继续保留，最终成功结果替换实时卡。

## 自动化验证

后端测试使用模型桩，不调用外部模型；PostgreSQL 集成仅使用连接私有 TEMP 表。前端使用 `ReadableStream` 和 mock fetch 验证实际 `streamQuestion`，不是只检查静态字符串。

- 初始摘要先于模型请求到达；简单张浩姓名查询仅调用证据解读模型，不调用计划模型。
- 快批次正文到达时，慢批次仍被测试事件阻塞；不等待所有批次。
- 引用/数量检查不通过的文本不会出现在流中；重复文本与完整性警告只输出一次。
- 流式正文拼接与最终答案一致；每批无损传递及重试回归继续覆盖。
- 后续结论前权限变化时，阻断该段输出并传播错误。
- 服务端 NDJSON 生成器在 worker 返回最终结果前交付首段；浏览器 reader 在后续 chunk 和 EOF 之前回调完整事件。
- 跨 chunk 残缺 JSON 正确缓冲；未收到 result 就 EOF 明确报未完成，已收到正文保留。
- 前端测试 15 项通过，类型检查和生产构建通过，已更新 `frontend/out`。
- 最终完整后端回归 147 项通过（`HBASK_INTEGRATION=1`），包含 PostgreSQL TEMP 表测试。

## 生效与边界

后端非热重载启动需要重启现有 FastAPI 服务，浏览器刷新后加载新静态资源；不要在已有 8088 监听时启动第二个服务。本次未自动停止或重启运行中的生产进程，未使用真实模型重测总耗时。

这是来源核验后的段落流式，不是未经核验的逐 token 输出。最慢批次可能仍需等待，模型总耗时并无固定承诺；停止等待不保证取消后台只读模型请求。来源与数字检查不等于完整语义证明。原有查询读取上限、分页、脱敏和业务授权不变。
